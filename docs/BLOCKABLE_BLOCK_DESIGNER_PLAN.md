# Blockable Block Designer 기획안

현재 프로그램 버전: `v1.2.1`
대상: VS Code Codex를 이용한 구현  
프로그램 형태: Python 데스크톱 도구  
출력 대상: React + Phaser 기반 Blockable 웹 게임

---

## 1. 문서 목적

이 문서는 Blockable 본 게임에서 사용할 **블록과 블록 조합 규칙을 시각적으로 설계하고 JSON 파일로 저장하는 Python 프로그램**의 기획 및 개발 기준을 정의한다.

이 프로그램은 Blockable 본 게임 자체가 아니다. 플레이어가 거푸집에 블록을 놓고 전투하는 기능을 구현하는 대신, 본 게임이 사용할 다음 데이터를 제작한다.

1. 블록의 `type`, 모양, 색상, 자체 효과
2. 같은 블록 또는 서로 다른 블록을 이용한 조합식
3. 조합식이 완성되었을 때 발생하는 효과
4. React + Phaser 게임이 불러올 수 있는 규칙 JSON

---

## 2. Blockable의 핵심 개념

### 2.1 거푸집

거푸집은 플레이어가 블록을 배치하는 격자 공간이다.

- 플레이어의 체력에 따라 본 게임에서 거푸집 크기가 달라진다.
- 체력이 감소하면 `3×3`을 중심으로 바깥쪽 칸이 하나씩 제거된다.
- 최소 크기는 `3×3`이다.
- 구체적인 체력 구간, 최대 크기, 축소 순서는 아직 확정하지 않는다.

체력에 따른 거푸집 축소는 **Blockable 본 게임의 책임**이다. 이 편집기는 해당 규칙을 계산하거나 저장하지 않는다.

### 2.2 블록

블록은 하나 이상의 격자 칸으로 구성된 배치 단위다.

각 블록은 다음 정보를 가진다.

- 고유 ID
- 표시 이름
- 사용자 정의 `type`
- 하나 이상의 칸으로 구성된 모양
- 색상
- 회전 및 좌우 반전 허용 여부
- 블록 자체 효과
- 설명과 태그

`기본 블록`, `고유 블록`, `코어 블록`, `저주 블록` 등을 프로그램 코드에 고정된 분류로 만들지 않는다. 필요할 경우 사용자가 `type`으로 생성한다.

예:

- `normal`
- `unique`
- `core`
- `curse`
- `weapon`
- `material`

위 이름은 예시일 뿐이며 type은 추가·수정·삭제할 수 있어야 한다.

### 2.3 조합식

조합식은 하나 이상의 블록을 특정 위치와 형태로 배치했을 때 완성되는 규칙이다.

조합식에는 다음과 같은 구성이 모두 가능해야 한다.

- 같은 블록 여러 개
- 같은 type에 속한 서로 다른 블록
- 서로 다른 type의 블록
- 같은 색상 또는 서로 다른 색상의 블록
- 특정 블록만 허용하는 자리
- type이나 색상 조건만 일치하면 되는 자리
- 여러 칸짜리 블록을 회전해 결합하는 구성

조합식은 단순히 “빨간색 블록 3개”와 같은 개수 조건만 저장하는 것이 아니다. **각 블록 조각이 격자의 어느 위치를 차지하는지**를 도면으로 저장할 수 있어야 한다.

## 3. 프로그램 목표

### 3.1 필수 목표

1. 블록 type을 자유롭게 관리할 수 있다.
2. 7개의 기본 색상을 제공하고 색상을 추가할 수 있다.
3. 격자를 클릭해 블록 모양을 만들 수 있다.
4. 블록에 자체 효과를 추가할 수 있다.
5. 생성한 블록을 조합식 격자에 배치할 수 있다.
6. 조합식에 동일하거나 서로 다른 블록을 여러 번 사용할 수 있다.
7. 조합식에 발동 효과를 추가할 수 있다.
8. 잘못된 데이터와 겹치는 배치를 저장 전에 검사한다.
9. 모든 규칙을 하나의 JSON 파일로 저장하고 다시 불러올 수 있다.
10. 출력 JSON을 React + Phaser 본 게임에서 파싱할 수 있다.

### 3.2 이번 프로그램에서 제외할 기능

- 실제 전투 진행
- 적 AI
- 플레이어 체력 계산
- 체력에 따른 거푸집 축소 계산
- 블록 드로우 및 주머니 확률
- 공격 애니메이션
- 조합 자동 탐색 및 자동 밸런싱
- 웹 게임 안에서의 조합 판정 구현
- JSON에 임의 Python 또는 JavaScript 코드를 저장해 실행하는 기능

## 4. 권장 기술 구성

### 4.1 MVP 기술

- Python `3.12` 이상
- GUI: 표준 라이브러리 `tkinter`
- 격자 편집: `tkinter.Canvas`
- 데이터 모델: `dataclasses`
- 파일 형식: UTF-8 JSON
- 테스트: `pytest`
- 코드 품질: `ruff`

초기 버전은 별도 GUI 프레임워크 없이 실행할 수 있는 단순한 데스크톱 프로그램을 목표로 한다. 향후 인터페이스가 복잡해질 경우 PySide6 전환을 별도 판단한다.

### 4.2 실행 예시

```bash
python -m blockable_block_designer
```

테스트:

```bash
pytest
```

## 5. 용어 및 데이터 구분

| 용어 | 의미 |
|---|---|
| Block Type | 사용자가 만드는 블록 분류 |
| Block Definition | 한 종류의 블록에 대한 원본 정의 |
| Shape Cell | 블록 모양을 이루는 상대 좌표 한 칸 |
| Block Instance | 조합식 안에 실제로 놓인 블록 한 개 |
| Combination | 여러 Block Instance로 구성한 조합식 |
| Effect | 블록 자체 또는 조합 완성 시 본 게임이 처리할 결과 |
| Effect ID | 본 게임이 알고 있는 효과 동작의 식별자 |
| Parameters | 피해량, 횟수, 지속 시간 등 효과별 입력값 |

Block Definition과 Block Instance를 반드시 구분한다. 예를 들어 `red_bar` 블록 하나를 조합식에 세 번 배치하면 정의는 하나지만 인스턴스는 세 개다.

## 6. 기본 색상

초기 기본 색상은 다음 7개다.

| ID | 이름 | 권장 표시색 |
|---|---|---|
| `red` | 빨간색 | `#E53935` |
| `orange` | 주황색 | `#FB8C00` |
| `yellow` | 노란색 | `#FDD835` |
| `green` | 초록색 | `#43A047` |
| `blue` | 파란색 | `#1E88E5` |
| `indigo` | 남색 | `#3949AB` |
| `purple` | 보라색 | `#8E24AA` |

색상 목록은 코드 상수가 아니라 프로젝트 데이터로 관리한다.

- 새로운 색상 추가 가능
- 표시 이름과 HEX 값 수정 가능
- 이미 블록이 사용 중인 색상은 경고 없이 삭제할 수 없음
- 프로젝트 ID는 공백 없이 자유롭게 지정 가능

## 7. 주요 화면 구성

프로그램은 한 창 안에서 다음 탭 또는 좌측 메뉴를 제공한다.

### 7.1 프로젝트

- 새 프로젝트
- JSON 열기
- 저장
- 다른 이름으로 저장
- 최근 저장 상태 표시
- 저장되지 않은 변경 내용 경고

### 7.2 Type 관리

- type 목록
- type 추가, 수정, 삭제
- type ID
- 표시 이름
- 설명
- 표시용 아이콘 또는 색상은 향후 확장

type을 삭제할 때 해당 type을 사용하는 블록이 있다면 삭제를 막고 사용처를 표시한다.

### 7.3 색상 관리

- 기본 7색 목록
- 색상 추가, 수정, 삭제
- 색상 미리보기
- 블록 사용 여부 표시

### 7.4 블록 편집기

화면 구성:

- 왼쪽: 블록 목록 및 검색
- 가운데: 블록 모양 격자 Canvas
- 오른쪽: 속성 및 효과 편집

필수 동작:

1. 빈 격자의 칸을 클릭해 활성화 또는 비활성화한다.
2. 활성 칸들의 집합이 블록 모양이 된다.
3. 분리된 블록 모양도 허용하되 검사 결과에 경고를 표시한다.
4. 저장할 때 좌상단을 원점 `(0, 0)`으로 좌표를 정규화한다.
5. 최소 한 칸이 있어야 한다.
6. 블록 ID, 이름, type, 색상을 지정한다.
7. 회전 허용과 반전 허용 여부를 지정한다.
8. 자체 효과를 0개 이상 지정한다.
9. 블록을 복제하거나 삭제할 수 있다.

### 7.5 조합식 편집기

화면 구성:

- 왼쪽: 사용할 수 있는 블록 목록과 필터
- 가운데: 조합식 격자 Canvas
- 오른쪽: 조합식 정보, 인스턴스 정보, 효과 편집

필수 동작:

1. 블록 목록에서 블록을 선택한다.
2. 격자를 클릭해 블록 인스턴스를 배치한다.
3. 배치 전 또는 배치 후 블록을 회전할 수 있다.
4. 블록 설정이 허용할 경우 좌우 반전할 수 있다.
5. 배치된 인스턴스를 선택, 이동, 삭제할 수 있다.
6. 서로 다른 인스턴스의 칸이 겹치면 배치할 수 없다.
7. 같은 Block Definition을 여러 번 배치할 수 있다.
8. 모든 배치 좌표는 저장 시 전체 조합의 좌상단을 기준으로 정규화한다.
9. 조합식 이름, ID, 설명, 태그를 입력한다.
10. 조합 완성 효과를 1개 이상 지정할 수 있다.
11. 현재 조합식의 입력값을 명시적으로 적용하는 저장 버튼을 제공한다.

### 7.6 검사 결과

저장 또는 내보내기 전에 전체 데이터를 검사하고 다음을 목록으로 표시한다.

- 오류: 게임용 정상 데이터로 사용할 수 없는 문제. 초안 저장은 허용한다.
- 경고: 저장할 수 있지만 확인이 필요한 문제

항목을 클릭하면 해당 type, 색상, 블록 또는 조합식 편집 화면으로 이동한다.

## 8. 효과 시스템

### 8.1 기본 원칙

편집기는 효과의 동작 코드를 직접 저장하지 않는다. 본 게임에 구현된 효과를 다음 형태로 참조한다.

```json
{
  "effect_id": "deal_damage",
  "parameters": {
    "amount": 10,
    "target": "enemy"
  }
}
```

이 구조를 사용하는 이유:

- JSON 안에 실행 코드를 넣지 않는다.
- Python 편집기와 TypeScript 게임이 동일한 데이터를 사용할 수 있다.
- 본 게임에서 구현되지 않은 효과를 명확히 검출할 수 있다.
- 수치만 변경해 밸런스를 조정할 수 있다.

### 8.2 효과 예시

초기 효과 ID 예시는 다음과 같다. 최종 목록은 본 게임 구현과 함께 확정한다.

- `deal_damage`
- `gain_block`
- `heal`
- `apply_status`
- `draw_block`
- `gain_gold`
- `modify_next_effect`

편집기는 효과마다 공통적으로 다음을 다룬다.

- `effect_id`
- 실행 순서를 위한 `order`
- 효과별 `parameters`
- 편집자용 설명

효과 편집 화면은 `effect_definitions.parameters`를 이용해 일반 입력 폼을
자동 생성한다. 사용자가 JSON 객체를 직접 작성하지 않아도 피해량, 개수,
지속 턴, 한글 버프명과 영문 버프 ID를 입력할 수 있어야 한다. `order`의 화면
표시 이름은 `효과 적용 순서`로 한다.

### 8.3 효과 정의 목록

가능하면 프로젝트 JSON에 `effect_definitions`를 포함한다. 각 정의는 편집기에서 필요한 입력 항목과 타입을 설명한다.

예:

```json
{
  "id": "deal_damage",
  "display_name": "피해",
  "parameters": [
    {
      "key": "amount",
      "value_type": "number",
      "required": true,
      "minimum": 0
    },
    {
      "key": "target",
      "value_type": "enum",
      "required": true,
      "options": ["enemy", "all_enemies"]
    }
  ]
}
```

MVP에서는 JSON 기반 정의를 읽어 입력 폼을 생성한다. 완전한 동적 스크립트 시스템은 만들지 않는다.

## 9. 조합식 표현 방법

### 9.1 정확한 블록 배치

조합식에서 각 블록 인스턴스는 다음 정보를 가진다.

- 인스턴스 ID
- 참조하는 Block Definition ID
- 조합식 내부 기준 좌표
- 회전값: `0`, `90`, `180`, `270`
- 좌우 반전 여부

블록 모양은 Block Definition의 상대 좌표에 변환을 적용해 계산한다.

### 9.2 조건형 슬롯

정확한 블록 ID 배치와 함께 다음 조건을 만족하는 블록 슬롯을 지원한다.

- 정확한 블록
- 임의 블록
- 특정 type
- 특정 색상
- 특정 태그

각 슬롯의 `block_id`는 도면에서 사용할 모양 템플릿이다. 조건형 슬롯에 들어오는
실제 블록은 템플릿과 변환 후 모양이 같고 슬롯 조건을 만족해야 한다.

### 9.3 조건부 효과와 공통 시너지

조합식은 항상 발생하는 `effects` 외에 `conditional_effects`를 가질 수 있다.
조건은 조합에 실제로 참여한 블록을 기준으로 판정한다.

- 모든 블록이 같은 색
- 모든 블록이 서로 다른 색
- 특정 색 포함
- 특정 색 개수
- 지정 색상 구성
- 모든 블록이 같은 type
- 블록 개수
- 태그 일치

프로젝트 최상위 `color_synergies`는 모든 조합식에 공통 적용할 조건부 효과를
저장한다. 따라서 같은 색 보너스를 조합식마다 반복해서 만들 필요가 없다.

### 9.4 조합의 회전 및 반전

조합식 전체에도 다음 설정을 둘 수 있다.

- `allow_recipe_rotation`
- `allow_recipe_mirroring`

예를 들어 세로 방향으로 등록한 검 조합을 가로 방향으로 놓아도 인정할지 결정한다.

### 9.5 비연결 조합과 빈 공간

조합식 안의 블록 인스턴스는 서로 상하좌우로 연결될 필요가 없다. 인스턴스
사이에 빈 칸이 있거나 대각선으로 떨어져 있는 구조도 정상 조합식으로 저장한다.
검증에서는 인스턴스 겹침과 참조 오류만 막으며 조합 전체의 연결성은 요구하지
않는다.

## 10. JSON 출력 계약

### 10.1 파일명

기본 출력 파일:

```text
blockable_block_design.json
```

### 10.2 최상위 구조

```json
{
  "schema_version": "1.1.0",
  "metadata": {},
  "colors": [],
  "block_types": [],
```

### 10.4 JSON 호환성 규칙

- 모든 ID는 프로젝트 안에서 고유해야 한다.
- 프로젝트 ID는 첫 글자, 언어, 대소문자를 제한하지 않으며 공백만 금지한다.
- 효과 ID, 버프 ID, 상태 ID처럼 게임 코드가 직접 참조하는 값은 영문 소문자
  `snake_case`를 사용한다.
- 좌표는 정수다.
- 색상은 `#RRGGBB` 형식이다.
- JSON에는 주석을 넣지 않는다.
- 저장 결과는 UTF-8과 들여쓰기 2칸을 사용한다.
- 객체 키 순서는 사람이 비교하기 쉽도록 일관되게 유지한다.
- 날짜는 ISO 8601 형식으로 저장한다.
- 숫자, 문자열, 불리언, 배열, 객체, `null`만 사용한다.
- `NaN`, `Infinity`, Python tuple 등 JavaScript JSON과 호환되지 않는 값을 사용하지 않는다.

## 11. 검증 규칙

### 11.1 오류

다음 문제는 정상 상태 저장 또는 게임용 내보내기를 막는다. 사용자가 명시적으로
확인하면 `validation_status: invalid`인 편집용 초안으로는 저장할 수 있다.

- 필수 ID 또는 이름 없음
- ID에 공백 포함
- 중복 ID
- 존재하지 않는 type 참조
- 존재하지 않는 색상 참조
- 블록 모양이 비어 있음
- 블록 모양의 칸 좌표 중복
- 허용되지 않은 회전 또는 반전 사용
- 조합식 안에서 블록 인스턴스끼리 겹침
- 존재하지 않는 블록 참조
- 존재하지 않는 effect ID 참조
- 필수 효과 parameter 누락
- parameter 자료형 불일치
- 조합식에 블록이 없음

### 11.2 경고

다음 문제는 경고로 표시한다.

- 어디에서도 사용되지 않는 type
- 어디에서도 사용되지 않는 색상
- 어떤 조합식에도 사용되지 않는 블록
- 자체 효과와 조합 효과가 모두 없는 블록
- 블록 모양이 상하좌우 기준으로 분리됨
- 이름은 다르지만 모양, type, 색상이 모두 같은 블록
- 완전히 같은 배치와 효과를 가진 중복 조합식
- 최소 `3×3` 거푸집에 들어가지 않는 조합식

`3×3`보다 큰 조합식은 게임 설계상 필요할 수 있으므로 오류가 아니라 경고다.

## 12. 저장 및 불러오기 동작

### 12.1 저장

1. 현재 편집 중인 입력값을 데이터 모델에 반영한다.
2. 전체 검증을 실행한다.
3. 오류가 있으면 오류 목록과 초안 저장 경고를 표시한다.
4. 사용자가 확인하면 오류가 있는 데이터도 편집용 초안으로 저장한다.
5. 경고가 있으면 사용자 확인 후 저장한다.
6. 임시 파일에 먼저 JSON을 기록한다.
7. 기록이 성공하면 대상 파일을 교체한다.

가능하면 저장 중 실패해 기존 정상 파일이 손상되지 않도록 원자적 저장 방식을 사용한다.

### 12.2 불러오기

1. JSON 문법을 검사한다.
2. `schema_version`을 확인한다.
3. 데이터 모델로 변환한다.
4. 전체 참조와 배치를 검증한다.
5. 데이터 오류가 있어도 편집 가능한 초안으로 열고 검사 결과를 표시한다.
6. JSON 문법 오류나 지원하지 않는 스키마는 읽기 실패로 처리한다.

알 수 없는 최신 필드가 있어도 가능한 경우 보존하거나 명확한 경고를 표시한다. 자동으로 데이터를 삭제하지 않는다.

## 14. 구현 단계

### 1단계: 데이터 모델과 JSON

- color, type, effect, block, combination 모델 구현
- JSON 저장 및 불러오기
- 좌표 정규화
- JSON round-trip 테스트

완료 조건:

- 예제 JSON을 읽은 후 다시 저장해도 의미가 동일하다.
- React/TypeScript에서 `JSON.parse()` 가능한 파일이 생성된다.

### 2단계: 블록 모양 편집기

- type 및 색상 관리
- 블록 목록 CRUD
- 클릭 방식의 모양 편집
- 연결성 및 중복 좌표 검사
- 블록 자체 효과 편집

완료 조건:

- 여러 모양과 색상의 블록을 만들고 다시 불러올 수 있다.

### 3단계: 조합식 편집기

- 블록 인스턴스 배치
- 이동, 회전, 반전, 삭제
- 겹침 방지
- 조합식 효과 편집
- 좌표 정규화

완료 조건:

- 같은 블록과 서로 다른 블록을 섞은 조합식을 시각적으로 만들 수 있다.

### 4단계: 전체 검증과 사용성

- 오류 및 경고 목록
- 저장되지 않은 변경 감지
- 파일 손상을 막는 안전 저장
- 키보드 단축키
- 선택 표시 및 격자 확대·축소

### 5단계: 본 게임 연동

- 본 게임 저장소에 JSON 로더 및 TypeScript 타입 작성
- JSON schema version 확인
- 블록 및 조합 판정 로직과 연결

본 게임 저장소 변경은 별도 작업이다. 이 편집기 구현 중 임의로 본 게임 코드를 수정하지 않는다.

## 16. MVP 완료 기준

다음 시나리오가 모두 성공하면 MVP를 완료한 것으로 본다.

1. 사용자가 `normal`, `unique`, `curse` 등 원하는 type을 만든다.
2. 기본 7색 중 하나 또는 새로 추가한 색상을 선택한다.
3. 1칸, 직선, L자 등 여러 블록 모양을 만든다.
4. 블록에 피해 또는 상태 효과를 지정한다.
5. 조합식 격자에 같은 블록 또는 서로 다른 블록을 여러 개 놓는다.
6. 블록을 회전해 하나의 완성 형상을 만든다.
7. 완성 조합에 별도의 효과를 지정한다.
8. 잘못 겹친 배치와 끊어진 참조를 프로그램이 검출한다.
9. `blockable_block_design.json`을 저장한다.
10. 저장한 파일을 편집기에서 다시 열었을 때 동일한 블록과 조합식이 복원된다.
11. 웹 게임에서 파일을 `JSON.parse()` 할 수 있다.

## 17. Codex 구현 지침

VS Code Codex는 다음 원칙을 지킨다.

1. 한 번에 전체 프로그램을 만들지 말고 구현 단계별로 작업한다.
2. 각 단계 시작 전에 현재 파일 구조와 기존 코드를 확인한다.
3. UI보다 데이터 모델, 좌표 변환, 검증, 저장 형식을 먼저 완성한다.
4. type 이름과 색상 종류를 하드코딩하지 않는다.
5. `basic_blocks`, `unique_blocks`처럼 블록 목록을 고정 분리하지 않는다.
6. 모든 블록은 하나의 `blocks` 목록에 저장하고 `type_id`로 분류한다.
7. Block Definition과 조합식의 Block Instance를 서로 다른 모델로 구현한다.
8. 게임 로직을 표현하는 임의 코드를 JSON에 저장하지 않는다.
9. 효과는 `effect_id + parameters`로 저장한다.
10. tkinter 객체를 domain 및 persistence 모듈로 전달하지 않는다.
11. 좌표 관련 로직은 순수 함수로 만들고 단위 테스트를 작성한다.
12. 저장 파일 스키마를 변경하면 `schema_version`과 예제 JSON을 함께 갱신한다.
13. 기존 데이터와 호환되지 않는 변경을 임의로 하지 않는다.
14. 범위가 불명확한 게임 규칙을 추측해 확정하지 말고 TODO로 남긴다.
15. 체력에 따른 거푸집 축소 로직은 구현하지 않는다.
16. 본 게임 저장소 수정, Git 커밋, 푸시는 사용자의 명시적 허가 전에는 수행하지 않는다.

## 18. 아직 확정하지 않은 항목

다음 항목은 프로그램 구조를 막지 않으므로 추후 Blockable 전투 규칙과 함께 결정한다.

- 실제 블록 type 목록
- 각 색상의 전투 의미
- 효과 ID 전체 목록
- 블록 자체 효과와 조합 효과의 중첩 방식
- 둘 이상의 조합식이 동시에 성립할 때 처리 순서
- 조합 후 블록 소비 또는 유지 방식
- 조합식 전체의 회전·반전 인정 여부의 기본값
- 조건형 슬롯 후보가 여러 조합식에 동시에 일치할 때의 우선순위
- 조합식 크기 제한
- 거푸집 바깥 또는 제거된 칸과의 판정

이 항목들은 현재 임의로 구현하지 않는다. MVP는 규칙 데이터를 안정적으로 **정의하고 저장하는 기능**에 집중한다.
